# Transaction review, signing and retry safety (Issue #25)

All Solo-X wallet transactions are restricted to devnet or a local validator. **Never use real funds.**

## User flow

1. Connect a compatible test wallet and enter the currency mint(s), recipient account if needed, and amount.
2. Select **Review transaction**. Solo-X checks the configured RPC/network, token accounts and sufficient balance before assembling a transaction.
3. Inspect the **action, network, connected wallet, source mint, destination mint/account, exact entered amount and notes**. Currency creation shows the newly generated mint and associated state/vault; its initial supply is zero and network/account-creation fees apply.
4. Select **Confirm review & sign**. The wallet is checked again before signing and before sending. You can cancel the review without signing.
5. The frontend prevents further submissions while signing, confirming, or reconciling a possibly broadcast transaction.

## Confirmation and retry policy

- A wallet rejection before signing does **not** submit a transaction. The user can start a fresh review.
- A transaction's signature is derived from the signed bytes *before* sending. If the RPC returns an error after signing, submission is **ambiguous**: the transaction may still be in the cluster. The UI retains the signature and blocks another attempt.
- **Recheck on-chain status** uses `getSignatureStatuses` with `searchTransactionHistory: true`. Confirmed/finalized success clears the pending lock. Explicit on-chain error clears it with a failure warning.
- A processed status or a missing history record while the blockhash is live remains **pending**. RPC failures keep retry blocked.
- If the transaction is **not found in RPC history and its last valid block height has passed**, a new reviewed attempt is permitted. Consult another independent RPC/explorer when the history result is uncertain.
- No transactions are automatically re-signed or rebroadcast with a new blockhash. Every retry needs a new review and wallet approval.
- An expired blockhash at review time requires building and reviewing a fresh transaction.

## Security limitations

Wallet prompts are generated by the wallet extension, not by this frontend; inspect them independently. The review uses the configured RPC which can be compromised, stale, or unavailable. A confirmation is not evidence of fiat redeemability or audit. This implementation deliberately does not persist pending status across page refreshes; **after reloading, inspect wallet history and the Solana explorer before attempting a similar operation**. Browser/validator integration needs manual test wallets and funded devnet fixtures.
